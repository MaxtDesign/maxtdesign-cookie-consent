# v1.9.0 — Extensibility Release: Scope

**Status:** **APPROVED 2026-07-20** — decisions locked (§7: category **Option 1**; **drop** `mdcc_consent_recorded` → Pro; **pair** the EU dark-pattern warning; docs **extend** `JAVASCRIPT-API.md` + publish at maxtdesign.com/cookie-consent/developers/). Implementation on `feat/extensibility-api`.
**Baseline:** free plugin 1.8.0 live (SVN r3615713).
**Why:** This is the **gate** for Cookie Consent Pro (strategy `ops/strategy/cookie-consent-pro-plan.md` §2/§7.1). Pro must plug into a stable public API instead of monkey-patching. The API also has standalone value for third-party integrators. **No licensing, no pricing, no Pro code here — free plugin only.**

Grounded in the actual 1.8.0 source, not the strategy draft's sketch. Two of the draft's six hooks changed on contact with reality (§3).

---

## 1. Design principles (non-negotiable)

1. **Zero-footprint preserved (hard rule 3).** The JS API ships *inside the already-enqueued* `consent-runtime.js` — no new asset, no new HTTP, no DB. PHP filters run server-side at render. Current frontend is 7.76 KB of a <10 KB budget → **~2 KB headroom; measure every addition.** If the API can't fit, lazy-load the service layer.
2. **Backward compatible.** Every existing `window.mdccConsent` method (`current/stored/acceptAll/acceptAnalyticsOnly/declineAll/reset`) and the `mdcc:changed` event stay byte-compatible. Locked `mdcc_` prefix, no namespace, `MDCC_` classes — unchanged (registry).
3. **The hooks are a contract.** Once shipped and documented, they're a public API with a stability guarantee (`mddcConsent.apiVersion`). Design them to outlive Pro v1.0.
4. **Free plugin never learns about Pro.** No "is Pro active" checks. Pro consumes; free exposes.

---

## 2. What already exists (1.8.0) — the starting point

- **JS `window.mdccConsent`:** `current()`, `stored()`, `acceptAll()`, `acceptAnalyticsOnly()`, `declineAll()`, `reset()`. Guarded by `if (window.mdccConsent) return;` (load-order matters — see §5).
- **DOM event** `mdcc:changed` (`detail` = state) on `document`.
- **State shape (fixed):** `{analytics: bool, ads: bool}` — validated in `readStoredState()`, defaulted in `MDCC_Consent_Manager::get_default_state()`. Maps to GCM v2 (`analytics_storage`; `ad_storage`/`ad_user_data`/`ad_personalization`) and the WP Consent API (`statistics`/`marketing`; `functional` always-allow).
- **PHP hooks already live:** `mdcc_should_show_popup`, `mdcc_consent_type`, `mdcc_consent_api_enabled`, `mdcc_consent_runtime_deps`.
- **Anchor points for new hooks:** `MDCC_Consent_Manager::inject_gcm_default()` (GCM default), `MDCC_Popup_System::render_popup()` (popup HTML), `MDCC_Admin_Settings` 5× `add_settings_section()` (admin), the enqueue path (services).

## 3. The v1.9.0 API surface

### 3a. JS additions (over the existing `mdccConsent` object)

| Method | Signature | Behavior |
|---|---|---|
| `registerService` | `registerService(id, { category, onGrant, onRevoke })` | **The headline Pro-enabler.** Registers a consent-gated service (each Pro pixel = one service). On register, **immediately** fires `onGrant`/`onRevoke` per current state; on every change, fires the transition. Idempotent per `id`. Handles Pro-loads-after-free (re-fires on register). |
| `getCategory` | `getCategory(name) → bool` | Reads `current()[name]`; `'functional'` always `true`. |
| `on` / `off` | `on(event, cb)` / `off(event, cb)` | Subscribe to `'change'` (wraps `mdcc:changed`, fires with state). Formalizes the event as API. |
| `requireConsent` | `requireConsent(category, cb)` | Runs `cb` now if granted, else once on next grant (one-shot). |
| `apiVersion` | `mdccConsent.apiVersion = '1'` | Stability contract for integrators. |

All existing methods unchanged.

### 3b. PHP filters (the free→Pro contract)

| Filter/Action | Anchor | Purpose |
|---|---|---|
| `mdcc_tracking_services` (filter, array) | enqueue path | Register server-known tracking services (`id => ['label','category','enqueue_gate']`). Lets Pro register FB Pixel/Hotjar/etc. server-side; the runtime gates their load. |
| `mdcc_consent_categories` (filter, array) | popup + admin + JS localize | Canonical category list + labels (`analytics`, `ads`, `functional`). **v1.9.0: labels/metadata only** (see §4 category decision). |
| `mdcc_gcm_default_state` (filter, `$state`, `$region=null`) | `inject_gcm_default()` | Lets Pro set **regional** GCM defaults (the geolocation feature). v1.9.0 ships the filter; region detection is Pro's. |
| `mdcc_admin_settings_sections` (filter) | 5× `add_settings_section()` | Lets Pro add its own settings sections/pages under the plugin menu. |
| `mdcc_popup_html` (filter, `$html`, `$settings`) | `render_popup()` | Lets Pro inject category checkboxes / customize popup markup. |

### 3c. CHANGED from the strategy draft (§2) — grounded corrections

- **`mdcc_consent_recorded` (server-side PHP action) — DROPPED from free.** The plugin is deliberately client-side/localStorage/zero-DB. A server-side action fired on every consent change requires a REST round-trip that **violates the zero-footprint promise**. This capability *is* the Pro analytics dashboard's capture path (strategy §3 Group C, approach B: opt-in REST + `wp_mdcc_pro_consent_stats` table) → **it belongs in Pro, not free.** Free equivalent already exists: the `mdcc:changed` event + the new `on('change')`.
- **JS `registerService/on/getCategory/requireConsent`** — the draft listed these; confirmed they build cleanly over the existing object.
- **`mdcc_popup_html` (filter) → `mdcc_popup_before_actions` (action).** `render_popup()` echoes inline (each element escaped). A full-HTML filter would force `echo $filtered_html` in the *free* plugin → Plugin Check `OutputNotEscaped` error. An action where add-ons echo (and escape) their own markup, placed before the action buttons, serves the same use case (Pro category checkboxes) and keeps the free plugin's Plugin Check clean.
- **`mdcc_admin_settings_sections`** implemented as an **action** (fires after core `add_settings_section()` calls, passing the page slug + option group), not a filter — the natural WP idiom for "register your own sections."

## 4. The crux decision — category model

Categories are hardcoded to `{analytics, ads}` (both PHP and JS). Extending them touches state shape + validation + GCM mapping + WP-Consent-API mapping + popup UI + admin fields + localStorage migration.

**Recommendation for v1.9.0 — Option 1 (keep 2 stored axes, expose category-aware API):**
- Keep `analytics` + `ads` as the canonical *stored* consent axes (they map 1:1 to GCM v2 and the WP Consent API — this is a feature, not a limitation) plus the always-on `functional`.
- `mdcc_consent_categories` exposes them with labels/metadata so integrators read/register against them.
- **All of Pro v1.0's integrations fit these axes:** FB Pixel = `ads`, Hotjar = `analytics`, LinkedIn = `ads`, TikTok = `ads`, custom scripts pick an axis. So arbitrary categories are **not needed to unblock Pro**.
- Ship in ~1.5–2 weeks.

**Option 2 (arbitrary stored categories now):** bigger — localStorage shape migration + remapping + popup redesign. ~doubles effort and adds upgrade risk. **Defer** to a later release if a real need appears (e.g. a distinct "preferences" category). Flag for operator.

## 5. Risks & edge cases

1. **Frontend budget.** The service registry + 4 methods add ~1–1.5 KB to `consent-runtime.js`. Currently 7.76 KB / 10 KB → measure; keep lean or lazy-load if it breaches.
2. **Load order.** `if (window.mdccConsent) return;` means if Pro's script loads first, free's runtime bails. Mitigation: `registerService` re-fires on register, and Pro declares free's runtime as a script dependency (`mdcc_consent_runtime_deps` already exists). Document the contract.
3. **Popup is inlined from disk** (`MDCC_Popup_System::get_popup_javascript()` reads `popup.js`). `mdcc_popup_html` must apply at PHP render time, before inlining.
4. **`mdcc_gcm_default_state` timing.** `inject_gcm_default()` runs early (before tracking). The filter must not add latency or async work — it's a synchronous array filter only.
5. **API stability.** Once documented, integrators depend on it. Version it (`apiVersion`) and treat changes as breaking.

## 6. Scope boundary

**IN v1.9.0:** the 5 PHP filters (§3b) + the JS API additions (§3a) + `apiVersion` + inline PHPDoc/JSDoc + public dev docs (extend `docs/JAVASCRIPT-API.md` → also publish at maxtdesign.com/cookie-consent/developers/) + tests + a version bump. Optionally pair with **one** user-visible polish item so users see a reason to update (candidate: the EU dark-pattern warning on reprompt, from the deferred list — low effort, not the Pro-owned GCM-region work).

**OUT (deferred / Pro):** arbitrary stored categories (§4 Option 2); `mdcc_consent_recorded` server-side action + any REST/DB (Pro); region *detection* (Pro geolocation); any tracking-service *implementations* (Pro); GCM region *defaults* data (Pro — free only ships the filter).
